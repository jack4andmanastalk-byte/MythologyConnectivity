# グラフのパス接続性はどの程度「有効」か — 現状の解説（2026-11-28）

対象: 本リポジトリの埋め込みグラフ（v17 凍結 HTML、297 ノード / 597 エッジ）と、それを用いた
パス・接続性に関する記述（`docs/v18_method_and_results.md` §7、`docs/interactive_graph_html_ja.md`、
`docs/v17_integrity_verification_report.md`、`docs/v17_network_attachment_verification_20261127_ja.md`、
`docs/registry.md`）およびデータ群（`derived/v17_html_embedded_data.json`、`data/frozen/*`、
`derived/html_embedded_v17_audit.json`）。

本書は**新しい仮説の検定ではない**（`docs/registry.md` への枝の追加は行っていない）。既存の
検証済み数値と、凍結データから再計算できる記述統計を突き合わせ、「パスの接続性」という
主張が現状どこまで支えられているかを切り分けるための解説である。

---

## 0. 結論（要約）

| 主張の種類 | 現状の評価 | 根拠の所在 |
| :--- | :--- | :--- |
| (1) 297 ノード / 597 エッジのグラフとして**構造が健全**（DAG・参照切れ 0・自己ループ 0・重複 0） | **有効**（機械検証済み） | 検査 B1–B3, B7 / `registry.md` 枝 #3 |
| (2) **古事記ノードに到達するパスが存在する**（37/37 話が親を持つ、経路は分断されていない） | **有効**（ただし条件付き） | 本書 §2 の再計算（B19 の「弱連結 3 成分」の内訳もここで確定） |
| (3) そのパスが**西ユーラシアにまで遡る**（メソポタミア・エジプト・ギリシャ・インド等） | **弱い（間接的・1 本の鎖に依存しうる）** | §3。直接流入は 0 本、すべて 2 ホップ以上の中継 |
| (4) 個々のエッジ（＝パスの各辺）が**データから再現できる** | **部分的（全体 61% / 古事記流入辺 33%）** | §4。凍結行列からの再計算 |
| (5) ノードに表示される**被説明率（パスの説明力）**が画面のエッジから導ける | **古事記 37 話では導けない**（表示は 3 層分解由来）。乖離 21 話 | `derived/html_embedded_v17_audit.json` / ADR 0003 |
| (6) 「構造がある」ことの**統計的有意性** | **有効**（全 281 ノードで p = 0.005） | 検査 E-cosine / E-calibrated、§7 表 8 |
| (7) 「**最長の伝播経路 8,451 km**」等の長距離接続の記述 | **距離・重みとも再計算できるが、古事記への経路ではない** | §5 |
| (8) 第 2 層（王権・儀礼・レガリア 15 次元）の**パスとしての意味** | **情報を認めない**（p = 0.498、d = −0.04） | `v18_method_and_results.md` §4.2、`registry.md` #1 |

**一言で言えば**: 「グラフとしての骨格と到達可能性」は有効だが、「個々のパスが何を意味するか」は
部分的にしか有効でない。とくに (a) 古事記へ流入する 126 本のうち凍結 75 次元行列から重みを
再現できるのは 42 本（33%）にとどまる、(b) 西ユーラシアへの接続はすべて中継ノード経由（直接辺 0 本）で、
中継ノードの辺の再現性に依存する、(c) ノードに表示される被説明率は画面のエッジから
再計算できない、という 3 点が「パスの有効性」の上限を決めている。

## 1. 前提: どのパスを「接続性」と呼んでいるか

リポジトリには方向の異なる 2 つの「経路」概念があり、混同すると評価を誤る。

| 層 | 実体 | データ | 意味 |
| :--- | :--- | :--- | :--- |
| **A. 可能性の層** | 交易路オーバーレイ 12 ルート | `data/trade_routes.json` | 物品・情報が**移動可能だった**ことの近似。解析計算には未使用（表示専用） |
| **B. 実証の層** | モチーフ伝播グラフ 597 エッジ | `derived/v17_html_embedded_data.json` | モチーフの**共有**が記録された辺。`source → target` は「先行 → 後行」 |

`docs/interactive_graph_html_ja.md` は A を「可能性のレイヤー」、B を「実際に移動した情報の実証層」と
位置づけている。「パスの接続性の有効性」を問う場合、A は交易史学の知見の近似（本リポジトリの
検証対象外）、B が本題である。以下 B のみを扱う。

なお B には 4 つの層ラベルが混在する（検査 C2）: `L1_myth` 489 / `L2_ext` 85 / `L2_dom` 18 / `L1+L2` 5。
パスの意味は「どの層の辺を辿ったか」で変わる。

## 2. 有効な部分 — 到達可能性と構造

凍結埋め込みデータ（`derived/v17_html_embedded_data.json`、原本 SHA-256 照合済み）から再計算した。

| 指標 | 値 | 解釈 |
| :--- | ---: | :--- |
| 弱連結成分 | 3（295 + 孤立 2） | 実質 1 つの連結グラフ。孤立は `NO07` / `EX16`（検査 B19 と一致） |
| 自己ループ / 重複 / 参照切れ | 0 / 0 / 0 | 健全（B1–B3） |
| DAG（Kahn 整列） | 297 / 297 | 全ノードが整列可能。時間逆行辺 0（`t_eff` 差と `dt` も全 597 本で一致） |
| 古事記 37 話の親（入辺） | 126 本（`external` 110 + `LP` 16） | **37 話すべてが 1 本以上**の親を持つ（入次数 1–6、中央値 3） |
| 古事記からの出辺 | **0 本** | 「古事記は親になれない」規則のとおり（検査 B21） |
| 根（入次数 0） | 31 | パスの始点候補 |
| 最長パス（有向） | 17 エッジ | 例: `MS_U02`(前2400) → … → `K1-05`(712)（メソポタミア→インド→イラン→仏教→ステップ→朝鮮→シベリア→古事記） |
| 古事記 37 話の祖先集合 | 中央値 53（最小 2 / 最大 88） | 1 話あたり中央値 53 ノードが「先行文脈」として繋がっている |
| 古事記の祖先集合の和 | 141 / 297 ノード | パスの上流は全ノードの約 47% を覆う |
| 全 597 本のうち古事記への祖先パス上にある辺 | 352 本 | グラフの約 59% が古事記に至る経路上 |
| 古事記集合とその他を分かつ**辺連結度** | 126 | 1 本の辺を切っても分断されない（冗長な接続） |
| 西ユーラシア地域と古事記の**辺連結度** | 53 | 同様に冗長。ただし後述の「鎖依存」は経路の**意味**の話 |

**ここまでは有効である。** 「古事記 37 話が、ユーラシアの神話ノード群からなるグラフに
到達可能な形で接続されている」ことは、構造検査と独立再計算の両方で確認できる。
検査 B19 が `warn`（弱連結 3 成分・孤立 2）としているのも、この 2 ノードが孤立しているだけで、
連結性の実質的な欠陥ではない。

### 2.1 ただし「密な接続」の見かけには注意（探索的・未登録）

以下は登録外の参考計算であり、判定には使わない。

- 古事記 37 話の祖先集合は中央値 53 ノード。しかし、**同じ入次数を保ったまま、リポジトリ自身の
  時空間適格判定（`src/engine.build_eligibility`）の範囲で親をランダムに選び直す**と、
  祖先集合の中央値は 34.4 ± 5.0（200 回）になる。観測値 53 はこの帰無分布の 100 百分位にある。
- つまり「祖先が多い」こと自体は、**グラフの次数構造と時空間ゲートからある程度自動的に出る**
  量ではなく、観測値の方が明確に大きい。この方向の「到達可能性の豊かさ」はデータ固有である。
- 一方で、これは**モチーフの意味的対応の証拠ではない**。同じ手続きを「再現可能な辺のみ」に
  制限すると、観測値は中央値 7、帰無は 7.3 ± 1.6（36 百分位）となり、差は消える（§4 参照）。

## 3. 弱い部分 — 「西ユーラシアまで遡る」は中継に依存する

`docs/interactive_graph_html_ja.md` の考察は「古事記以前にユーラシア東端から西端まで
リレー式の接続が成立していた」と述べ、その傍証としてモチーフ伝播グラフの長距離辺を挙げる。
この主張の**グラフ側の強さ**は次のように整理できる。

| 事実（597 本の再計算） | 値 |
| :--- | ---: |
| メソポタミア・エジプト・ギリシャ・インド・アナトリア・イラン → **古事記への直接辺** | **0 本** |
| 古事記への直接の流入元の地域 | シベリア 33 / 中国 27 / 朝鮮 27 / 東南アジア 19 / 列島前史 13 / ステップ 7 |
| 西ユーラシア（上記 6 地域）から古事記集合への経路長 | 最短 2 ホップ（29 話）、3 ホップ（7 話）、経路なし（1 話 = `K1-18`） |
| 西ユーラシア発で古事記の祖先パス上にある辺 | 146 本 / 597 |
| 古事記の祖先集合に含まれる西ユーラシア・ノード | メソポタミア 30 / インド 24 / エジプト 9 / イラン 5 / ギリシャ 3 / アナトリア 2（延べ） |

つまり **古事記と西ユーラシアの接続は、すべて「シベリア・中国・朝鮮・東南アジア」など
中間地域のノードを経由した 2〜3 ホップの中継**である。これは異常ではない
（地理的距離と時間差を考えれば自然な形）が、次の 2 つの帰結を持つ。

1. **経路の有効性は中継ノードの辺の質に依存する。** 西→古事記の直接証拠ではなく、
   「西→中継」「中継→古事記」の 2 本の辺がそれぞれ妥当かで決まる。
2. **中継ノードを 1 つ外すと経路が消える場合がある。** 無向グラフの橋（bridge）は 26 本あり、
   そのうち 3 本（`SE01–K1-08`、`SI12–K1-22`、`SE02–K1-18`）は**片側に古事記ノードが 1 つだけ**
   乗っている。この 3 話は、その 1 本の辺が妥当でなければ上流全体への接続を失う。
   `K1-18`（木花之佐久夜毘売と石長比売）は、西ユーラシアへの経路を持たない唯一の話である。

また、`docs/interactive_graph_html_ja.md` が例示する古事記への親エッジは、
**重みがデータから再現できる辺**（§4 参照）と、そうでない辺が混在している。

| 例（同書の記載） | 距離 | Δt | 表示重み | 75D 行列からの再計算コサイン | 一致 |
| :--- | ---: | ---: | ---: | ---: | :---: |
| `CN04 → K1-02` | 2,982 km | 512 年 | 0.949 | 0.949 | ○ |
| `SE08 → K1-01` | 4,078 km | 512 年 | 0.667 | 0.667 | ○ |
| `SI09 → K1-01` | 4,474 km | 1,212 年 | 0.370 | **0.667** | × |

`SI09 → K1-01` は「シベリア→K1-01（4,474km・Δt=1,212年）」の例として引かれているが、
表示重み 0.370 は原文行列のコサイン 0.667 と一致しない（差 0.297）。
`tests/test_interactive_html.py` は**距離と Δt のみ**を照合しており、重みの再現性は検査していない。

## 4. 「辺の再現性」の実測 — ここが最大の制約

`docs/v18_method_and_results.md` §7 は「独立実装が描く辺は v16 の 494 本と 255 本しか重ならない
（Jaccard 0.349）」と報告している。本節はそれを**辺の種類別**に分解したものである
（凍結 `data/frozen/l1_75d_legacy_matrix.csv`（281×75、非零 1,500 セル）から再計算）。

### 4.1 全体

| 比較 | 値 |
| :--- | ---: |
| 両端が L1 行列に含まれる表示エッジ | 533 / 597 |
| うち 表示重み = 生コサイン（±5e-4） | **312（58.5%）** |
| うち 表示重み = 生コサイン（±0.01） | 325（61.0%） |
| うち 表示重みとコサインが 0.1 以上ずれる | **142（26.6%）** |
| 重み > 0 なのにコサイン = 0（＝特徴量の共有が 1 次元もない） | **18 本（すべて古事記への流入辺）** |
| 各ターゲットの最大重み辺（第 1 ステップ相当、249 本）のうち ±5e-4 で一致 | 205（82%） |

### 4.1b 剥離ステップ別の一致率（重みの順位をステップの代理指標にした記述統計）

埋め込みデータには剥離ステップ番号が無いため、ターゲットごとに重み降順の順位で近似した。

| 重み順位（ステップの代理） | 辺数 | 重みとコサインが 0.1 以上ずれる | 不一致率 |
| :--- | ---: | ---: | ---: |
| 1 | 249 | 21 | 8% |
| 2 | 181 | 67 | 37% |
| 3 | 85 | 44 | 52% |
| 4 以上 | 18 | 10 | 56% |

**第 1 ステップに相当する辺はほぼ再現し、2 ステップ目以降は再現しない**という明確な勾配がある。
v17 の被説明率は 3 親までの貪欲剥離で計算されるため、**上流の 2・3 本目の辺が再現しないことは
最終的な被説明率の再現性に直結する**（検査 D2/D3 の乖離と同じ方向）。

### 4.2 古事記への流入辺に限った内訳（最重要）

| 区分 | 本数 | 備考 |
| :--- | ---: | :--- |
| 古事記への流入辺 合計 | 126 | `external` 110 + `LP` 16 |
| うち L1 行列の両端が揃い、重み = 生コサイン（±0.01） | **42** | 検証可能 |
| うち上記以外（重みがコサインで説明できない／LP 起点の L2 辺） | **68 + 16 = 84** | 再計算不能 |
| **再現可能率** | **33%（42/126）** | |

すなわち、**古事記の「先行被説明率」を支えるパスの辺のうち、約 3 分の 2 は凍結行列から
独立に再現できない**。これは不正の証拠ではない（v17 のエッジは剥離エンジンの 2 ステップ目以降や
L2 層の寄与を含むため、単純な生コサイン一致を期待できない設計になっている）。
しかし「パスが何を根拠に描かれているか」を外部の読者が検証できる範囲は、この 3 分の 1 に限られる。

### 4.3 「再現可能な辺だけ」に絞ると何が残るか

表示エッジのうち、①重みが生コサインで再現できる L1 内部辺、②LP 起点の L2 辺（生成規則 C1 で
仕様として説明済み）だけを残すと **369 本（62%）** になる。この部分グラフでは:

| 指標 | 全 597 本 | 再現可能 369 本のみ |
| :--- | ---: | ---: |
| 古事記 37 話の祖先集合 中央値 | 53 | **7** |
| 西ユーラシア祖先を持つ話 | 36 / 37 | 31 / 37 |
| 祖先集合の帰無分布（同次数・時空間適格）に対する百分位 | 100% | **36%（差なし）** |
| 古事記への流入辺 | 126 | **58**（うち `LP` 由来 16）。37 / 37 話が 1 本以上を保持 |

**解釈**: 「祖先が多い／接続が豊か」という見かけは、**再現性の低い辺が担っている**。
再現可能な辺だけでは、接続の豊かさは同次数ランダムグラフと区別できない。
これは §7 表 8 の「構造は再現するが個々の辺は実装依存」という結論を、接続性の側から
具体的に裏づける結果である（参考計算・未登録）。

## 5. 「最長伝播距離 8,451 km」等の記述の位置づけ

`docs/interactive_graph_html_ja.md` は最長エッジ `IN_B07 → NO13`（8,451 km、Δt 1,000 年、重み 0.416）と、
6,000 km 超が 22 本あることを挙げ、実際の移動の証拠としている。データ上の値は正しく、
**重みも独立再計算できる**（凍結 75 次元行列のコサイン 0.4161、差 0.0001）。

| 確認項目 | 結果 |
| :--- | :--- |
| 最長エッジ `IN_B07 → NO13` の端点が L1 行列に含まれるか | 両方含まれる（再計算可） |
| その重みの再現 | 0.416 対 コサイン 0.4161（一致） |
| 6,000 km 超の 22 本のうち重みが再現できるもの | 18 / 22（4 本は 0.1 以上ずれる） |
| この辺は古事記への経路か | **いいえ**。インド（仏教）→ 北欧・ケルトの辺で、古事記ノードは端点でない |

したがって「8,451 km の辺が存在する」ことは有効な記述だが、これは**古事記への接続の証拠ではない**
（古事記へ流入する 126 本の辺の中央値は 1,596 km、最大は `ST_E01 → K2-05` の 6,056 km。例示されている 4,474 km は上位に入る長い辺である）。§3 のとおり、
古事記と西ユーラシアの接続は中継ノード経由の短い辺の連鎖で構成されている。

## 6. 表示される「パスの説明力」— 画面からは再計算できない

`derived/html_embedded_v17_audit.json`（ADR 0003）が示すとおり、ノードの `explained_pct` は
3 系統の混成である。

| 出所 | ノード数 | 内容 |
| :--- | ---: | :--- |
| `v16.L1` | 244 | v16 単層の剥離値 |
| `decomp.total_final` | 37 | 3 層分解（L1 + L2ext + L2dom）の合成値。**古事記 37 話** |
| `pureL2_dom` | 16 | 純第 2 層の剥離値（LP13–16 等） |

古事記 37 話はすべて `decomp.total_final` であり、画面に描かれている L1 エッジから
再計算した値とは 21 話で 0.01 以上ずれる（最大は `K1-05`: 表示 0.707 対 再計算 0.2332、差 −0.4738）。
**「このパスでこの話の 70.7% が説明される」と画面から読むことはできない。**
この点は ADR 0003 で「凍結原本は改変せず、台帳と注記で運用する」と決定済みであり、
`docs/interactive/graph_network_atlas.html` には乖離バッジと注記が実装されている
（`make interactive` で再生成してもバイト単位で同一であることを本日確認）。

統計的な位置づけも併記しておく。第 2 層（15 次元）の主検定は p = 0.498、効果量 d = −0.04、
FDR 有意 0 / 25 話であり、**「パスが王権・儀礼・レガリアのモチーフを偶然以上に説明する」
という主張は支持されない**（`registry.md` #1、#7）。第 1 層（75 次元）は p = 0.005、d = 5.61 で
陽性対照として成立している（同 #2）。

## 11. 並列実行（GitSwarm 型運用）への耐性 — 実測

§2.5 の「残る限界」を、実際に並列で走らせて測った。結論は **「読み取り専用の並列は安全。
書き込みを伴う並列は安全ではない」**。以下はすべて本リポジトリ上での実測値。

### 11.1 測ったこと

| # | 実験 | 結果 |
| ---: | :--- | :--- |
| 1 | `src/run_all.py` を **同一 `outputs/` に対して 2 本同時**に実行 | **2 本とも exit 0、`results.json`（時刻除く）とレポートが完全一致**、`check_determinism` も 17 ファイル不一致 0 |
| 2 | `src/work_scheduler.py claim` を **6 本同時**に発行 | **勝者 1 本（`w3`）、敗者 5 本は正しく拒否**。`fcntl.flock` による排他が機能 |
| 3 | 同一 `outputs/` へ 1 本の書き手＋3 本の読み手 | 読み手の **6810 回が JSONDecodeError（部分読み）**、成功 1061 回 |
| 4 | 同一 `outputs/` へ 4 本の書き手＋読み手 | 読み手の **3340 回が部分読み**（JSON は必ず壊れ得る） |
| 5 | CSV を書きながら `pandas.read_csv` | **エラー 958 回 / 行数不足 306 回**（成功 265 回） |
| 6 | `git add` の同時実行 | **`fatal: Unable to create .git/index.lock: File exists`** |

### 11.2 なぜ 1 が通ってしまうのか（危険な理由）

2 本同時でも結果が一致したのは、**出力が決定的（同じ入力・同じコード・同じシード）だから**であって、
**競合が無いからではない**。実験 3〜5 が示すとおり、同じ `outputs/` を共有している限り、

* 書き込み中の `results.json` / `*.csv` を読むと**必ず壊れた中間状態が読める**（`write_text` は原子的でない）。
  本リポジトリで原子的な書き込みを使っているのは `verify_network.py`（ステータス JSON のみ）と
  `work_scheduler.py`（状態ファイルのみ）で、**`run_all.py` の 17 生成物はすべて非原子的**。
* `run_all.py` は `manifest.sha256` を「その時点のファイル」から作るので、
  他プロセスが書き込み中だと**マニフェストだけが別時点を指す**ことがある（実験 1 で偶然一致しただけ）。

つまり **「たまたま一致した」を「並列安全」と読んではいけない**。

### 11.3 安全に並列化できる範囲

| 並列化のしかた | 判定 | 条件 |
| :--- | :--- | :--- |
| 読み取り専用の解析（`verify_doc` / `check_registry` / `verify_numbers` / テスト） | **安全** | `outputs/` を書かないこと |
| `work_scheduler.py` による作業の取得 | **安全** | 同一ワークスペース＋同一ファイルシステムが前提（実測で確認） |
| **同一 `outputs/` への `make run` の同時実行** | **不安全** | 生成物が壊れた中間状態で読まれ得る |
| 同一ワークスペースでの同時 `git commit` / `git add` | **不安全** | `index.lock` で失敗する（実測） |
| 別ワークスペース（別クローン）での実行 | **安全** | ただし `.work_scheduler` の排他は効かない（別 FS のため） |
| `vendor/` を共有したままの `make network` の同時実行 | 条件付きで安全 | 出力が `outputs/` のみで、他は読むだけ |

### 11.4 推奨する運用（GitSwarm 型）

1. **1 ワークスペース = 1 書き込み者**。並列にしたいのは「読む作業」と「別クローンでの作業」だけにする。
2. 複数ワーカーを並列に走らせる場合は、**`OUT` を分ける**（`outputs/w1/`, `outputs/w2/` など）か、
   ワーカーごとに別クローンを使う。`config/analysis.json` の `outputs` を切り替えられるようにするのが本筋。
3. `make run` を同時に走らせざるを得ない場合は、**`work_scheduler.py` で `RUN-PIPELINE` タスクを
   排他取得してから実行する**（スケジューラは正しく排他する。実測 11.1-2）。
4. CI は 1 ジョブ 1 ワークスペースなので、現状の並列 CI は問題ない。危険なのは**同じワークスペースを
   共有する複数の対話セッション**。

### 11.5 実装上の改善候補（未着手）

* `outputs/` への書き込みを `tempfile` + `os.replace` に統一する（`verify_network.py` と同じ方式）。
  これで「読者が壊れた JSON を掴む」問題は消える（書き手同士の上書きは残る）。
* `run_all.py` の冒頭で `outputs/.lock` を `flock` し、二重起動を**失敗させる**（黙って上書きしない）。
* ワーカーごとの出力先を `config/analysis.json` で切り替え可能にする。

いずれも本レビューの範囲外なので、着手する場合は `docs/registry.md` に枝を追加してから行う。

## 12. 「1 ワーカー = 1 ブランチ」で足りるか — 実測

§11 の続き。**「1 ワーカーに 1 ブランチを割り当て、マージ時に main を再検証する」だけでは不十分**である。
理由は 3 つあり、いずれも本リポジトリで再現した。

### 12.1 ブランチはワークスペースを分けない（最も危険）

`git checkout` は**同じ作業ディレクトリの中身を書き換える**。したがって同一ワークスペースで
2 ブランチを同時に走らせると、**実行中のプロセスが読むコードが途中で変わる**。

実測（`/tmp` の最小再現）:

```
worker=W1 start_branch=featA start_code=print("A")
worker=W1 end_branch=featB   end_code=print("B")      ← 同じプロセスが別ブランチのコードを読んだ
```

**1 ワーカー = 1 ブランチは、1 ワーカー = 1 ワークスペース（または `git worktree`）と
セットでなければ意味がない。** 本リポジトリは `outputs/`（`tracked=1`）と `.venv/`・`vendor/`・
`.work_scheduler/`（すべて追跡外）をブランチ間で共有するため、ブランチを分けても
**出力先と実行環境は 1 つ**のままである。

`git worktree` を使えば、`index` が worktree ごとに分かれるため **`index.lock` の衝突も消える**
（実測: 2 つの worktree から同時コミットが成功）。ただし `.git` のオブジェクトストアは共有なので、
**同一ブランチを 2 つの worktree で同時に checkout することは git が拒否する**（これは安全側の設計）。

### 12.2 「マージ時に再検証する」は、このリポジトリでは自動化されていない

| 確認項目 | 実測結果 |
| :--- | :--- |
| PR の CI は何を検査するか | `pull_request` イベントで **head SHA** を checkout して検査（`656f02f` で確認）。**main とマージした結果ではない** |
| main のブランチ保護 | API が **403**（トークン権限不足）。`--merge` が `BLOCKED` になったので**保護は存在する**が、内容は読めない |
| マージ後の main の CI | `push` イベントで走る（`81da63a` で success）。**マージ後に初めて検証される**＝手遅れになり得る |
| 必須レビュー承認 | `reviewDecision` は空。必須化されているかは不明 |

つまり現状は **「PR 単体が green → マージ → main で CI が走る」** という順序で、
**壊れていれば main が赤くなってから気付く**。マージを止める仕組みにはなっていない。

### 12.3 両方 green でも、統合すると壊れる（意味的競合）

これが「1 ブランチ = 1 ワーカー」で防げない本命の失敗。実測:

1. workerB のブランチで `docs/peer_review_summary_ja.md` の「古事記 37 話」を **40 話**に改ざん。
2. workerB 単独では **ゲートが通ってしまった**（`[OK] 違反 0 件`）。原因は `context_allow` に
   **「対象」** という語が入っており、`…（古事記 40 話＋比較地域）を対象とする…` の行が <!-- doc-number-exempt -->
   **行ごと免除**されていたこと。**これは実際にあったバグで、本日修正した。**
3. workerA（無関係な事前登録＋config 追加）と workerB をマージすると、**main 相当のツリーで違反 1 件**。
4. 修正版ゲートなら、**workerB 単独の時点で落ちる**（`古事記 40 話 -> 期待 37`）。 <!-- doc-number-exempt -->

教訓は 2 つ。

* **ゲートは「行の語彙」ではなく「文法」で切る。** 語彙の許可リストは、頻出語（「対象」「うち」）を
  入れた瞬間に**行全体の免除**になり、ゲートが無効化される。現在は
  `古事記\s*(\d+)\s*話(?!\s*[のにをへ（(])` として、**直後に助詞が続くものだけ**を部分集合として扱う。
* **意味的競合はマージ前にしか検出できない。** 両ブランチが独立に green でも、統合後に
  初めて矛盾が現れる。検出するには「**main を取り込んだ状態で**ゲートを回す」必要がある。

### 12.4 したがって、こう運用すれば「大丈夫」

| 層 | 必要な条件 | 現状 |
| :--- | :--- | :--- |
| ワークスペース | **1 ワーカー = 1 クローン or 1 `git worktree`**（ブランチだけ分けても不十分） | ❌ 本リポジトリは単一ワークスペースを共有 |
| 出力先 | ワーカーごとに `outputs/` を分ける、または `flock` で排他 | ❌ 全ワーカーが `outputs/` を共有 |
| ブランチ | 1 ワーカー = 1 ブランチ | ✅ 運用で担保 |
| マージ前 | **main をマージした状態で**ゲートを再実行（`git merge origin/main` → `make all`） | ❌ 未自動化（PR の CI は head SHA のみ） |
| マージ後 | main の CI が green | ✅ 動いている（ただし事後） |
| 意味的競合 | マージ結果に対する検証 | ❌ 未実施（今回の実験で必要性を確認） |

**答え**: 「1 ワーカー = 1 ブランチ」＋「マージ時に main を再検証」は**必要条件であって十分条件ではない**。
次の 3 つが揃って初めて安全になる。

1. **1 ワーカー = 1 ワークスペース**（`git worktree` でよい。ブランチの分離だけでは足りない）
2. **マージ前に `origin/main` を取り込んでゲートを回す**（`pull_request` の CI は head しか見ない）
3. **出力先の分離または排他**（`outputs/` を共有したまま `make run` を並列実行しない）

### 12.5 実装候補（未着手）

* CI に `merge_group` トリガー、または `git merge origin/main` してから `make all` する job を追加する
  （これが「マージ時に再検証」の実体）。
* `make gate` を新設し、`git fetch && git merge --no-commit origin/main` → `make all` → `git merge --abort`
  を 1 コマンドにする。
* `run_all.py` の冒頭で `outputs/.lock` を `flock` する（§11.5 と同じ）。

いずれも本レビューの範囲外。着手する場合は `docs/registry.md` に枝を追加してから行う。

## 13. 別リポジトリ（AIselfMySelf）のハーネスとの比較

同じアカウント運用者が並列セッションで使っている `aiselfmyselfresearch-max/AIselfMySelf` のハーネスを
実際に読み、本リポジトリと突き合わせた。**§12 で「未解決」と書いた 3 つの問題のうち、2 つは
あちらでは解決済み、1 つは本リポジトリの方が進んでいる。**

### 13.1 決定的な違いは「書き込み先が競合しない形になっているか」

| 項目 | 本リポジトリ | AIselfMySelf |
| :--- | :--- | :--- |
| 並列の単位 | ブランチ（ワークスペースは共有） | ブランチ＋**セッション専用シャード** |
| 書き込み先 | `outputs/`（**全員が同じ場所**） | `state/<collection>.d/<date>-<suffix>.jsonl`（**セッションごとに別ファイル**） |
| 追記の衝突 | `write_text` で上書き（非原子的、§11 で 6810 回の部分読みを実測） | `open(path, "ab")` で末尾追記＋`flock`（`ledger_io.exclusive_lock`） |
| ID の採番 | なし（連番・固定値） | `tools/new_id.py` が `PREFIX-YYYYMMDD-xxxxxx`（6 桁乱数）を採番し、**全シャードの和集合と照合して衝突を避ける** |
| 既存行の保護 | なし（書き換え自由） | `tools/append_only_check.py` が **バイト単位**で「基底の全行が残っているか」を検査。上書き指定は無い |
| 生成物の競合 | なし | `BELIEF_MAP.md` / `READING_MAP.md` は**手でマージしない**。`--check-map` で鮮度を検査し、競合したら**再生成**で解決 |
| マージ時 | CI は head SHA のみ（§12.2） | `.arena/resolve_merge.py` が `origin/main` を取り込み、**既知の競合（生成物 2 件＋予算値 1 件）だけを機械解決**。未知の競合は `exit 2` で止める |

**核心**: あちらは「**書き込み先を分ける**」ことで競合を**構造的に**減らし、残った競合
（生成物・予算値）だけを決定的な手順で解いている。本リポジトリは「**同じ場所に書く**」ので、
並列化した瞬間に §11 の破損が起きる。**ハーネスの差であって、規律の差ではない。**

### 13.2 あちらでも「1 ブランチ = 1 ワーカー」だけでは足りていない（重要な共通点）

あちらの `docs/parallel-work.md` は 1,160 行あり、**同じ問題で何度も事故を起こして対策を積んだ記録**になっている。

* 「並行統合は、対象を選んだ時点では衝突しないと確認できても、マージ時点で衝突しうる」
  （2026-11-07 実測: 別ルートで同じ 8 行が移され、マージ直後に `read_id` が 8 件重複）
* `gh pr view --json files` は**その時点の差分**しか返さない。他 PR が吸収する範囲はそれより広い
* シャード名を散文（`readings/`）に書くと、そのシャードは**移動不能**になり統合候補から外れる
  （実測: 自己所在地を書いた 158 行のうち **116 行**が現存しないパスを指していた）

つまり **「1 ワーカー = 1 ブランチ」は、あちらでも必要条件であって十分条件ではない。**
違いは「足りない部分を埋める道具があるか」で、あちらにはある（本リポジトリには無い）。

### 13.3 本リポジトリの方が進んでいる点（過小評価しないこと）

| 項目 | 本リポジトリ | AIselfMySelf |
| :--- | :--- | :--- |
| **マージの強制力** | `strict_required_status_checks_policy: true`（ruleset `main`、active）→ **main が進むと PR は `BEHIND` になりマージ不可**（PR #18 で実測: `mergeStateStatus=BEHIND`、`gh pr merge` が拒否） | main は `protected: true` だが **required check は `validate` 1 本のみ**。`.github/workflows/main-guard.yml` のコメントが「**main は required check が通っていないマージを受け入れる**」と明記し、`tools/main_guard.py --strict` で**毎日赤くして警告**している（＝直せていない） |
| 事前登録の順序検査 | `src/check_prereg.py` が **git 履歴から**「登録が設定変更より先か」を機械検査 | 該当なし（台帳の追記専用性で代替） |
| 数値のドリフト防止 | `src/verify_numbers.py`（§10-4、文法規則で総数を検査） | `--check-map` 系（生成物の鮮度のみ） |
| 決定性の検査 | `src/check_determinism.py`（2 回実行して 17 ファイル一致） | 該当なし |

**あちらが「強い」のは並列書き込みの設計**、**こちらが「強い」のはマージの強制力と数値の統制**である。
どちらが上という話ではなく、**解決している問題が違う**。

### 13.4 応用できる仕組み（優先度順）

| # | 仕組み | なぜ効くか | 本リポジトリへの適用 |
| ---: | :--- | :--- | :--- |
| 1 | **書き込み先の分離**（セッション別シャード） | §11 の破損（部分読み 6810 回・CSV 958 エラー）は**すべて「同じファイルに書く」ことが原因**。分ければ構造的に消える | `outputs/` を `outputs/<session>/` にし、`config/analysis.json` の `outputs` を切替可能にする。`derived/` は**追記専用の JSONL シャード**にする |
| 2 | **原子的書き込み**（`tempfile` + `os.replace`） | 読者が壊れた中間状態を掴まない。§11.5 で挙げた候補 | `run_all.py` の 17 生成物すべて。`verify_network.py` は既に実装済み（同じ方式を横展開するだけ） |
| 3 | **`--check-map` 型の鮮度検査** | 生成物を手でマージしない規律を機械化できる | `outputs/report.md`・`manifest.sha256` に「再生成で解決する」規則を明記し、`--check` を追加 |
| 4 | **`.arena/resolve_merge.py` 相当**（既知の競合のみ機械解決、未知は停止） | マージ時の手作業を減らしつつ、**知らない競合を黙って解決しない** | `make gate`（§12.5）の中に「`origin/main` を取り込む → 既知の生成物競合だけ再生成 → 未知は `exit 2`」を実装 |
| 5 | **`new_id.py` 相当の衝突回避 ID** | 連番は並列で必ず衝突する | 枝 #8〜#11 の ID は既に固定文字列なので不要。**将来、`outputs/` をシャード化するなら必要** |
| 6 | **`append_only_check.py` 相当のバイト検査** | 「解析してから見る」検査は再直列化を見逃す | `docs/registry.md` の既存行と `data/frozen/` に適用可能。**凍結データの不変性検査**として価値が高い |
| 7 | **`main_guard.py` 相当の「直せない設定を毎日可視化する」** | 設定はコードで直せない。だが**赤くし続ければ忘れない** | 本リポジトリは ruleset が既に `strict` なので不要。**逆に、あちらへ本リポジトリの ruleset 設定を移植する方が価値が高い** |

### 13.5 注意（そのまま移植してはいけないもの）

* `resolve_merge.py` は **`REPO` がハードコード**されている（`/home/user/AIselfMySelf`）。移植時は `git rev-parse --show-toplevel` にする。
* `readings/` の「シャード名を散文に書かない」規律は、**あちらで 1,160 行の事故記録から導かれたもの**。
  本リポジトリの文書はファイル名を普通に参照するので、**そのまま適用すると文書の書き方を全部変えることになる**。
  適用するなら「`derived/` をシャード化するときだけ」に限定する。
* あちらの `size_budget.py` は**上限を上げるたびに根拠を文書に残す**運用。これは本リポジトリの
  `exemption_budget`（§11 で 8→10 に上げた際に理由を `config` に書いた）と同じ発想で、**既に実践している**。

### 13.6 結論

* **「1 ワーカー = 1 ブランチ」だけでは、どちらのリポジトリでも足りない。** あちらは
  「**書き込み先を分ける**」ことで足りない部分を埋め、こちらは「**マージを強制的に止める**」ことで埋めている。
* 本リポジトリに**最も効く 1 つ**は **`outputs/` のセッション別分離**（§13.4 の #1）。
  これは §11 で実測した破損の**直接の原因**に対する処方であり、`derived/` の設計を変えずに始められる。
* 逆に **AIselfMySelf に移植すべきは、本リポジトリの ruleset 設定**（`strict_required_status_checks_policy: true`）。
  あちらは main が required check 未通過のマージを受け入れる状態が**文書化された既知の欠陥**として残っている。

いずれも本レビューの範囲外。着手する場合は `docs/registry.md` に枝を追加してから行う。
