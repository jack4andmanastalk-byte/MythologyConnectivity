# リポジトリをハーネスとする運用（GitSwarm 型）の設計判断

対象: v17 / v18 の検証プロジェクト
日付: 2026-11-27
状態: 提案（ADR 0001 の草案）

---

## 0. 結論

**リポジトリ運用に移すべきである。ただし「GitSwarm」＝エージェントを多数並列に走らせる部分には、
独立性の幻想という固有の危険がある。** リポジトリ化そのものは今回の作業で見つかった弱点のうち
3 つを確実に潰すが、残り 2 つは潰さない。切り分けて導入するのが正しい。

| 今回見つかった弱点 | リポジトリで解決するか |
| :--- | :--- |
| 数値と本文の食い違い（85.44% 対 82.17%、表示値の混成） | **解決する**（CI が毎コミットで照合し、失敗したらマージできない） |
| 手書き定数（変換 42/52 対、回廊半径、しきい値） | **解決する**（監査スクリプトを CI ゲート化。差分レビューで必ず目に入る） |
| 判定基準を結果より先に固定したことの証明 | **解決する**（事前登録ファイルのコミット時刻が客観証拠になる） |
| 評定の独立性（α = 0.755 は同一評定主体の再現性にすぎない） | **解決しない**（体制の問題。エージェントを増やしても同じ系統なら相関誤差が増えるだけ） |
| 個々の辺が実装依存（Jaccard 0.349） | **部分的**（実装を増やすと「どの辺が安定か」は見えるが、正解は決まらない） |

## 1. なぜ zip 運用が限界に来ているか

今回のセッションで実際に起きたこと:

1. v17 は zip で届き、検証のたびに `work/run_v17` へ展開し直した。**どの版を検証したかは
   md5 を手で控えるしかない**（実際、HTML だけは再生成でバイト一致しなかった）。
2. 私（エージェント）は v18 を新規に作り直したが、**v17 と v18 の差分が「別ディレクトリ」としてしか
   存在しない**。どこで数値が変わったかを `diff` で追う手段がない。
3. 判定基準（p<0.05 かつ d≥0.8 かつ α≥0.667）を結果を見る前に固定したが、**その順序を
   証明するものは何もない**。会話ログが唯一の証拠で、これは外部の査読者には渡せない。
4. レポートの数値が本文・表・図でずれた場合、気づく手段が「照合スクリプトを書く」しかない。
   今回それを書いたが、**走らせ忘れれば無意味**である。

いずれも「履歴・差分・自動実行」が無いことの帰結で、リポジトリが直接効く。

---

## 2. リポジトリが買うもの（この案件に即して）

| 能力 | 具体的な効き方 |
| :--- | :--- |
| 来歴の固定 | コミット SHA を全レポートに埋め込める。「この数値はこの入力・このコードの組から出た」と言い切れる |
| 事前登録の証明 | 判定基準を含む `config/analysis.json` と `docs/prereg/*.md` の**コミット時刻**が、結果コミットより前であることを機械的に示せる |
| CI ゲート | 検証・定数監査・文書照合・再実行一致を毎コミットで強制。落ちたらマージ不可 |
| 差分レビュー | 手書き定数の追加・削除が差分に出る。レビューで「なぜこの値を足したか」を要求できる |
| データの差分可能性 | バイナリ（zip / PNG / HTML）ではなく JSON / JSONL / CSV で持てば、意味のある差分が取れる |
| 蓄積 | ADR・Issue・PR・レポートが時系列で積み上がる。会話ログに依存しない |

特に効くのは **「HTML に埋め込まれた JSON を、リポジトリでは別ファイルにする」** こと。
今回 297 ノード / 597 エッジを検証して分かったのは、HTML はデータの入れ物としては
差分も検索もできず、混成（表示値の出所が 3 系統）に気づけないという点だった。

---

## 3. リポジトリが買わないもの（楽観してはいけない点）

1. **評定の独立性。** pass A と pass B の α = 0.755 は「同じ評定主体の再現性」であり、
   人間の研究者間一致ではない。エージェントを 10 体に増やしても、同じモデル系・同じ語彙・
   同じ指示なら誤差は相関する。独立性が要るなら**系統を変える**（別モデル系、人間による一部抽出監査、
   語彙を変えた第 3 者評定）しかない。
2. **正解の不在。** 辺が Jaccard 0.35 で食い違うとき、どちらが正しいかはデータで決まらない。
   リポジトリは「どれだけ食い違ったか」を残せるが、「どちらが正しいか」は決めない。
3. **入力の恣意性。** 75 次元・15 次元の語彙と水準は人が置いた値である。CI はそれを検査できない。
   （検査できるのは「コードに定数が漏れていないこと」まで。）

したがって「GitSwarm にすれば検証が精緻になる」は言い過ぎで、正しくは
**「リポジトリにすれば、恣意性がどこにあるかが露出し、恣意性を隠せなくなる」**。

## 4. 推奨構成（ハーネス）

```
repo/
├── README.md
├── Makefile                     # make all / make determ / make network
├── config/analysis.json         # 唯一の設定源（これも事前登録物）
├── docs/
│   ├── prereg/YYYYMMDD-<id>.md  # 仮説・指標・判定基準・停止規則（結果前にコミット）
│   ├── adr/0001-*.md            # 設計判断の記録
│   └── reports/                 # 手書きレポート（数値は機械照合）
├── data/
│   ├── frozen/*.csv             # 凍結入力（ハッシュを manifest に）
│   └── annotations/*.jsonl      # 評定（スキーマ検証・証拠引用つき）
├── src/                         # 決定論的パイプライン（ego を入れない）
├── outputs/                     # 生成物（追跡しない。CI が artifacts として保存）
└── .github/workflows/verify.yml # ゲート
```

押さえどころ:

* **`outputs/` はコミットしない。** 生成物は CI で作り、`manifest.sha256` と一緒に
  artifacts / Release に置く。コミットすると差分がノイズで埋まる。
* **`data/frozen` は不変。** 変更は新しいディレクトリ（`frozen_v2/`）を切る。上書き禁止。
* **レポートは数値を持ってよいが、必ず照合される。** 今回の `verify_doc.py`（58 項目照合）を
  CI に入れる。数値がずれた瞬間に落ちる。
* **大型バイナリ（HTML・PNG・zip）はコミットしない。** 中身の JSON を抽出して
  `derived/html_embedded_v17.json` として持つ（今回で言えば 297 ノード / 597 エッジ）。

## 5. GitSwarm の運用規則（並列化するなら）

並列エージェントを使うときの最低条件:

1. **1 ブランチ = 1 仮説 = 1 事前登録。** 事前登録なしのブランチは CI で落とす。
2. **系統を混ぜる。** 同一モデル系の並列は「多数決」ではなく「相関した複製」になる。
   少なくとも 1 系統は違うモデル系、または人間の抽出監査を入れる。
3. **反証係を必ず 1 つ置く。** 「この結論が誤りだとしたら、どの検査が落ちるか」を先に書かせる。
4. **合流は CI ゲート通過のみ。** 数値の突き合わせに失敗した枝は自動で捨てる。
5. **成果物は台帳で合流させる。** 各枝は `outputs/<branch>/results.json` を出し、
   合流コミットで差分表（どのノードで判定が変わったか）を作る。今回の
   `network_node_audit.csv`（297 行）がその雛形になる。

## 6. 移行手順（今回の成果物から）

1. `v18/` をそのままリポジトリのルートにする（構成は既に §4 とほぼ同じ）。
2. `outputs/` を `.gitignore` に追加し、`make all` で再生成できることを確認する。
3. `docs/prereg/20261127-layer2-verification.md` を**初回コミット**に含める
   （判定基準は既に `config/analysis.json` にある）。
4. CI（`.github/workflows/verify.yml`）を有効化し、最初の 3 コミットで
   validate / audit / doc 照合 / 再実行一致が緑になることを確認する。
5. そのうえで v17 側の検証（`network_verification`）を別ブランチで回し、
   合流時に `network_node_audit.csv` の差分をレビューする。

---

## 7. この判断の取り消し条件

次のいずれかが起きたら、この構成を見直す。

* CI の実行時間が 10 分を超え、日常のコミットを妨げる。
* 生成物の再現性が環境差（ライブラリ版）で崩れ、ロックファイルでは抑えられない。
* 並列エージェントの出力が照合を通過したまま意味を失う（例: 全枝が同じ誤りを共有する）。
